# Implementation Handoff

## When to load

- An approved design direction must become production frontend code.
- The current implementer needs concrete component, token, state, responsive, and verification requirements.

## When NOT to load

- Product flow or visual direction is still materially unresolved.
- The request is critique or ideation only.

## Core rules

- Translate intent into observable acceptance criteria without redesigning during handoff.
- Inventory existing components before naming new ones.
- Prefer installed, customized shadcn/ui primitives for accessible behavior; compose and style them to express the approved direction.
- Treat files generated by shadcn/ui as owned source code. Review diffs and never overwrite customization blindly.
- Add only required components with `npx shadcn@latest add <component>` after confirming project conventions and approval for dependency changes.
- Specify every interaction state, responsive transformation, content stress case, and accessibility behavior.
- Name browser viewports and checks that prove the implementation.

## Implementation checklist

Use this in the current session; a separate agent handoff is optional, not required.
For a bounded approved design, record only changed decisions and relevant checks.

1. Design thesis and non-goals.
2. Annotated content and hierarchy.
3. Layout behavior for narrow, middle, and wide ranges.
4. Token and typography changes using existing semantic roles.
5. Component map: reuse, extend, add, or custom-build with rationale.
6. State and interaction matrix.
7. Accessibility requirements.
8. Assets and exact content.
9. Acceptance criteria and browser verification plan.

## shadcn/ui component map

For each component record:

| Need                              | Existing project component       | shadcn/ui primitive | Decision | Customization                                        |
| --------------------------------- | -------------------------------- | ------------------- | -------- | ---------------------------------------------------- |
| Example: destructive confirmation | `components/ui/alert-dialog.tsx` | Alert Dialog        | Reuse    | Add `danger` action variant; preserve focus behavior |

Before adding anything, inspect:

```text
components.json
components/ui/
lib/utils.*
global stylesheet and semantic theme variables
package.json and framework configuration
existing feature-level compositions
```

Current official CLI patterns:

```bash
npx shadcn@latest info
npx shadcn@latest add alert-dialog
```

These are examples, not permission to run dependency-changing commands or overwrite files.

## Minimal examples

```md
Thesis: Calm editorial triage; hierarchy comes from type and rules, not stacked cards.
Reuse: Button, Badge, AlertDialog, Tooltip, Skeleton.
Extend: Button gets a compact `quiet` variant through the existing variant utility.
Add: None until the component inventory confirms the Sheet is absent.
Custom: Case evidence timeline, composed from semantic list markup; no new primitive library.
States: Loading skeleton preserves final geometry; inline failure keeps retry beside evidence; archive uses AlertDialog and an undo toast.
Responsive: 360px, 768px, and 1440px structural checks plus 200% zoom.
Accessibility: One h1, visible focus, named icon buttons, live result count, reduced-motion fallback.
Acceptance: Existing tests pass; keyboard workflow succeeds; no page-level horizontal overflow.
```

## Anti-patterns

- "Use shadcn" without naming components, variants, states, and customization.
- Installing all components or initializing shadcn/ui in an established project without approval.
- Replacing project-owned customized primitives with fresh generated files.
- Creating custom dialogs, menus, or tabs only to obtain a different appearance.
- Acceptance criteria based only on matching one screenshot.

## Checklist

- Existing components and theme conventions were inventoried.
- Every new or changed component has a reason and owner.
- shadcn/ui additions are minimal and safe for customized source.
- States, breakpoints, content stress, and accessibility are specified.
- Browser checks, tests, and non-goals are explicit.
